# Plan: History of Capacity Submissions per Session

## Goal

Keep a history of every capacity rating submitted for a session, rather than
overwriting the previous value. Today's "Override" dialog should be removed,
and the latest submission for a (date, slot) should be treated as the current
value in the overview and statistics.

---

## Recommendation: Approach 1 (one row per submission)

After analyzing both approaches against the existing code in `app.py` and
the Google Sheets API constraints documented in `AGENTS.md`, **Approach 1
(append a new row for every submission) is clearly the better choice.**

### Why Approach 1 wins

| Concern | Approach 1 (multi-row) | Approach 2 (CSV cell) |
|---|---|---|
| API calls per submit | **1** (`append_row`) | 2+ (`get_values` to read cell + `update_cell`) |
| Concurrency safety | Append is atomic; last writer naturally wins. No race window. | Read-modify-write race: two simultaneous writers can lose one value. |
| Code complexity | Removes `update_entry`, `confirm_override_dialog`, `fetch_recent_capacity`, and the entire override branch in the submit flow. | Adds string parsing (`.split(",")[-1]`) at every read site (`find_existing_entry`, overview, statistics, line chart). |
| Data model | Normalized; one fact per row. Easy to add a `Timestamp` or `Benutzer` column later. | Denormalized; awkward to extend without re-parsing the cell. |
| Pandas ergonomics | `find_existing_entry` already returns `.iloc[-1]`, so "latest wins" works **without changes**. | Every `Kapazität` access has to split + index. |
| Sheet growth | Linear in submissions (≈ a few hundred rows / year — trivial for Sheets). | Constant rows but cells grow unboundedly per slot/date. |
| Sheet readability for humans | Slightly more rows, but each row is self-explanatory. | One messy cell like `"Passt,Zu voll,Passt"` — no per-entry date/time. |
| Cell-size limit (50k chars) | Not applicable. | Theoretically reachable on a busy slot over years. |
| Statistics | Trivial: group by (Datum, slot) and take last, or count submissions per day. | Must explode comma list before any analysis. |

### Why the "sheet bloat" concern is not real

With ~20 sessions/week and conservatively 1.5 submissions per session,
the sheet grows by ~1,500 rows/year. Google Sheets handles millions of
rows. The existing range-limited reads (tail-only, scaled to Stammdaten
count) already prevent unbounded load times — we just bump the multiplier
slightly to account for occasional re-submissions.

## UX principle

From the user's perspective **nothing about the override flow changes**:
- The detail page still shows "Jemand anderes hat bereits **X** eingetragen."
- Pressing "Absenden" on a slot that already has an entry still opens
  `confirm_override_dialog` with the existing Abbrechen / Überschreiben
  buttons and the same warning copy.
- The overview still shows exactly **one** rating per slot ("Bereits
  erfasst" with the current label).

What changes is purely the storage layer: "Überschreiben" no longer
mutates the existing row. It appends a new row, and consumers
(overview + statistics) deduplicate to the latest entry per (date, slot).
Users are not told that previous values are retained.

## New column: `Eingetragen am`

Add a 7th column at the end of the Kapazität sheet that records **when**
each submission was added (wall-clock submission time), distinct from
`Datum` which is the *training* date the entry refers to. This is
particularly useful because users can backfill missing entries up to 2
weeks in the past.

### Schema

- **Column name**: `Eingetragen am`
- **Position**: appended after `Kapazität` (column G, 7th column).
- **Format**: ISO 8601 local datetime string (`YYYY-MM-DDTHH:MM:SS`),
  produced via `datetime.now().replace(microsecond=0).isoformat()`. No
  timezone suffix — the app runs in a known single-locale environment
  (Europe/Berlin) and ISO strings sort lexicographically, which keeps
  the `iloc[-1]` "latest wins" logic correct even when multiple
  submissions occur on the same `Datum`.
- **Backfill**: existing rows in the sheet will have an empty
  `Eingetragen am` cell. Code must tolerate missing/empty values
  (treat as `None` / empty string). No data migration is required —
  historical rows simply don't have a submission timestamp.

### Code changes for the new column

1. **`DATA_HEADERS`** (`app.py:92`-`99`): append `"Eingetragen am"` as
   the last entry.

2. **Range-limited reads**: both `fetch_all_initial` (`app.py:211`) and
   `fetch_recent_capacity` (`app.py:242`) currently read range `A:G`.
   With the new column they must read `A:H`. Update both string
   literals.

3. **`update_entry`**: being deleted (see Section 9 below), so no
   change needed.

4. **`submit_entry`** (`app.py:312`-`325`): add a `submitted_at`
   parameter (defaulting to `datetime.now().replace(microsecond=0).isoformat()`
   when not provided) and pass it as the 7th value in `append_row`.
   Computing the default inside the function body keeps call sites
   clean.

5. **`confirm_override_dialog`** (`app.py:416`): after Section 1+2
   below switch it to call `submit_entry`, the new timestamp column is
   filled automatically by `submit_entry`'s default.

6. **Cached row append**: both append sites that build a `new_row` dict
   (the normal submit branch at `app.py:1264`-`1274` and the override
   branch updated per Section 2 below) must include
   `"Eingetragen am": submitted_at` so the cache matches the sheet.
   Capture the timestamp once before the append (e.g. `submitted_at =
   datetime.now().replace(microsecond=0).isoformat()`) and pass it
   both to `submit_entry(..., submitted_at=submitted_at)` and into the
   cache row dict to guarantee they're identical.

7. **Statistics dedup ordering** (Section 7 below): when multiple
   submissions exist for the same (Datum, slot), `drop_duplicates(
   keep="last")` currently relies on row order in the sheet to mean
   "latest". With the explicit timestamp we can be safer:

   ```python
   if "Eingetragen am" in df.columns:
       df = df.sort_values("Eingetragen am", kind="stable")
   df = df.drop_duplicates(
       subset=["Datum", "Wochentag", "Uhrzeit", "Trainingsart", "Halle"],
       keep="last",
   )
   ```

   For rows missing `Eingetragen am` (historical data), pandas sorts
   `NaN` to the end by default — which would incorrectly mark them as
   "latest". Use `.fillna("")` before sorting so empty timestamps sort
   first (oldest), preserving correct "latest wins" semantics.

8. **`find_existing_entry`** (`app.py:286`-`309`): no functional change
   needed. `matches.iloc[-1]` continues to return the last row in
   insertion order, which after a fresh fetch is the latest submission.
   The timestamp column is along for the ride and accessible to callers
   if needed.

9. **Backfill UI display**: when a user opens a backfilled entry, no
   "Eingetragen am" value is exposed in the UI. This column is purely
   for audit / analytics. No UI work required.

10. **No UI exposure**: per user decision, `Eingetragen am` stays
    purely a sheet-side audit column. No tooltips, captions, or
    detail-page text reference it.

11. **Sheet-creation paths**: `_get_data_worksheet` (`app.py:260`-`271`)
    and `get_or_create_worksheet` already write `DATA_HEADERS`, so
    newly created sheets automatically get the new column. For the
    existing production sheet, the user must add the `Eingetragen am`
    header in column G manually (one-time, see "Migration" below).

12. **`_records_from_values`** (`app.py:155`): already generic
    (`dict(zip(headers, row))`) and tolerates short rows. With short
    rows produced before the column was added, the new key will simply
    be missing — pandas will fill with `NaN`. No change.

## Changes to `app.py`

### 1. Replace `update_entry` semantics with append

`update_entry` (`app.py:328`-`372`) is currently called from
`confirm_override_dialog` (`app.py:416`) and reads column A + a
last-500 range + does an `update_cell`. Two options:

**A. Replace the body of `update_entry` with an append** (keep the
function name & signature for minimal call-site churn), so it becomes:

```python
def update_entry(worksheet, today_iso, weekday, time_slot,
                 training_type, hall, capacity_label) -> None:
    """Append a new capacity entry. Latest row per (date, slot) wins."""
    worksheet.append_row(
        [today_iso, weekday, time_slot, training_type, hall, capacity_label]
    )
```

**B. Delete `update_entry` and call `submit_entry` directly** from
`confirm_override_dialog`.

Recommended: **B** — clearer intent, removes a now-misleading function
name. `submit_entry` (`app.py:312`) already does exactly the right
thing. Update the call site in `confirm_override_dialog` (`app.py:416`)
to `submit_entry(data_ws, t["Wochentag"], t["Uhrzeit"], t["Trainingsart"], t["Halle"], new_label, date_iso=entry_date)`.

### 2. Update the cache after a confirmed "override"

Today (`app.py:431`-`445`) the dialog updates the matching cached row
in-place via `data_df.loc[matching.index[-1], "Kapazität"] = new_label`.
Since `find_existing_entry` already returns `iloc[-1]`, this still
produces the correct overview reading.

To keep the cache representative of the on-sheet state (which now has
both the old and the new row), change this to **append** the new row
instead of mutating the old one:

```python
new_row = pd.DataFrame([{
    "Datum": entry_date,
    "Wochentag": t["Wochentag"],
    "Uhrzeit": t["Uhrzeit"],
    "Trainingsart": t["Trainingsart"],
    "Halle": t["Halle"],
    "Kapazität": new_label,
}])
st.session_state._cached_data_df = pd.concat(
    [data_df, new_row], ignore_index=True
)
```

This mirrors the existing append logic in the normal submit branch
(`app.py:1264`-`1274`). The `iloc[-1]` semantics in `find_existing_entry`
guarantee the overview will show `new_label`.

### 3. Submit branch (`app.py:1214`-`1289`) — keep override path

Keep the override-detection flow exactly as it is:
- Still call `fetch_recent_capacity` at submit time to pick up
  concurrent writes.
- Still call `confirm_override_dialog` when an existing entry is found.
- The normal "no existing entry" branch already appends — no change.

The only difference is that `confirm_override_dialog` now appends
instead of updating (per Sections 1 + 2).

### 4. Keep `fetch_recent_capacity`

Still needed for the concurrent-write check at submit time. No change.

### 5. Overview ("Bereits erfasst") — no code change

`find_existing_entry` already does `matches.iloc[-1]`, so the overview
naturally shows the **most recent** submission for each slot today.
Because submissions are appended in chronological order, `iloc[-1]` is
also the chronologically latest.

### 6. Detail-page hint copy — no change

The "Jemand anderes hat in der Zwischenzeit bereits **X** eingetragen…"
info box (`app.py:1198`-`1201`) and the override dialog copy
(`app.py:404`-`405`) stay as-is. From the user's perspective the
override flow is unchanged.

### 7. Statistics (`render_statistics`, `app.py:897`-`1139`)

Multiple submissions per (Datum, slot) would currently be averaged
together by the `groupby` in the weekly chart (`app.py:947`-`949`) and
plotted as separate points on the same date in the detail line chart
(`app.py:1117`-`1128`). Both behaviors should change so a single day's
"final" capacity is represented by the **latest** submission, with
intra-day re-submissions treated as corrections, not extra data points.

**Implementation:** at the top of `render_statistics`, after building
`df`, collapse to "latest per (Datum, Wochentag, Uhrzeit, Trainingsart,
Halle)":

```python
if not df.empty:
    # Latest submission wins per (date, slot). Row order in the sheet
    # is chronological, so keeping the last occurrence per group is
    # sufficient — no separate timestamp column needed.
    df = df.drop_duplicates(
        subset=["Datum", "Wochentag", "Uhrzeit", "Trainingsart", "Halle"],
        keep="last",
    )
```

This single change makes both the weekly heatmap and the per-slot trend
line use one data point per day, while still preserving the full
submission history in the sheet for audit purposes.

### 8. Range-limited reads (`fetch_all_initial`, `app.py:204`-`205`; `fetch_recent_capacity`, `app.py:235`-`236`)

Current formula: `rows_needed = max(100, entries_per_week * 2 * 2)` — i.e.
2 weeks × 2× buffer for "overrides".

With true history, the buffer should account for occasional
re-submissions. Bump the multiplier to give comfortable headroom:

```python
rows_needed = max(150, entries_per_week * 2 * 4)
```

(2 weeks × 4× buffer; floor raised from 100 → 150.) Apply the same
formula to `fetch_recent_capacity` so the submit-time concurrent-write
check also sees enough history.

`update_entry` (`app.py:328`-`372`) becomes unused once
`confirm_override_dialog` switches to `submit_entry`. Delete it.

## Migration / backwards compatibility

- **Row data**: no migration needed. Existing rows remain valid — each
  is treated as one historical data point. The first submission after
  this change for any slot that previously had a "final" overridden
  value will simply append a new row beneath it.
- **`Eingetragen am` column**: the user must manually add the header
  text `Eingetragen am` to cell **G1** of the Kapazität sheet **once**
  before deploying the new app version. Existing rows leave G2..Gn
  empty; the code tolerates this. New submissions write a timestamp
  there automatically. (Alternatively, the column header is created
  automatically only if the data sheet doesn't exist yet — see
  `_get_data_worksheet` at `app.py:260`-`271` — so for the live sheet
  it must be added by hand.)

---

## Decision: keep the static / canonical header approach

The dynamic-header proposal was considered and **rejected** for this
project. The sheet is not expected to be hand-edited — it's a passive
byte-store consumed by the app for reads and writes. Adding dynamic
header detection + validation would solve a problem (column reordering
via the sheet UI) that doesn't exist in this workflow, at the cost of
~30–50 lines of extra code and a new validation failure surface.

The current static approach (the immediate hotfix already shipped):
- `_records_from_values` uses `DATA_HEADERS` as canonical column names
  via the `headers=DATA_HEADERS` argument.
- Row 1 of the sheet is ignored for parsing; positions in
  `DATA_HEADERS` are the source of truth.
- Tail-slice path prepends `all_values[0]` so the row-0 skip in
  `_records_from_values` aligns correctly even when reading from the
  middle of the sheet.
- `submit_entry` writes a fixed-order list matching `DATA_HEADERS`.

This is **immune** to the failure mode that prompted the discussion
(duplicate `Kapazität` header in G1) because row 1's contents are
never consulted.

If a future maintainer ever needs to reorder columns in the sheet UI,
the dynamic-header proposal lives in git history and can be revived
then.
